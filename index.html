02Em uso

Daily Ops Dashboard

Quatro fontes agregadas à mão, todo dia, convergem num único guia de onde começar.

Problema
Todo dia a equipe agregava manualmente Zendesk, HubSpot, Drive e bases de SLA para decidir por onde começar — sem um critério único de criticidade.
Sistema
Painel 360 que consolida as 4 fontes com 14 regras de criticidade e gera automaticamente, toda manhã, um guia de priorização por analista (ou por time, para liderança): tickets a priorizar, faturas e bases por multibenefício (Vida, Academia, Mental, Pet, Farmácia) e calendário de prazos com particularidades por cliente.
Stack
SQL · Snowflake · IA generativa · Zendesk · HubSpot · Drive
~30 min / diade agregação manual substituídos

03Recomendada para o time

Motor de Triagem de Divergências

A conferência ticket por ticket vira um diagnóstico em que cada linha já chega classificada.

Problema
Divergências entre backoffice e fatura eram checadas manualmente, ticket por ticket, sem histórico de duplicidades nem validação cruzada de CPF e data.
Sistema
Diagnóstico com IA generativa: consolida os casos num painel único, identifica duplicidades e histórico de tratamento anterior, valida CPF e data de nascimento via integração com a Receita Federal (n8n) e automatiza a comparação linha a linha.
Stack
IA generativa · n8n · Receita Federal · validação de CPF/data
30–60 min → verificação diretapor ticket — aplicado a um backlog de ~200 tickets entre 8 analistas

TicketScript · 01 · Zendesk

Cada ticket pedia uma resposta padronizada.

Escolhida numa planilha de operadora × tipo de problema × resolução.

02 · Processo manual

Quatro passos manuais, em todo ticket.

Abrir o ticket, trocar de aba, copiar o script, voltar e colar — dezenas de vezes por dia. A linha errada virava o script errado enviado ao cliente.

03 · TicketScript

Uma extensão que lê o ticket aberto.

Extensão de navegador (Chrome/Edge) que cruza o texto do ticket com a planilha publicada em CSV, por correspondência de prefixo. A planilha segue como fonte editável pelo time; nada roda em servidor.

04 · Automação

4 passos → 1 clique.

O script entra no campo de resposta quando o analista aciona. Usado em produção até dar lugar ao FormPilot.

Uma pequena automação resolveu um problema recorrente.

Mas o problema não parava ali.

O esforço maior estava nas movimentações: cada inclusão, exclusão ou alteração exigia localizar o formulário da operadora, preencher campo a campo e enviar para assinatura num fluxo separado. E a extensão precisava ser instalada no navegador de cada analista.

FormPilot · 01 · Mapear

Cada operadora é mapeada uma vez.

Campos, posições e regras do formulário viram configuração (JSON). Uma operadora nova entra por arquivo, sem alterar código.

02 · Preencher

O próprio chamado preenche o formulário.

App nativo no Zendesk (ZAF), sem backend próprio. Lê os dados estruturados do ticket e estampa os campos no PDF via pdf-lib.

03 · Validar

Uma pessoa revisa antes de cada envio.

A automação cuida da leitura do ticket, do preenchimento e do envio. A revisão humana continua antes de cada envio.

04 · Assinar

Do chamado à assinatura, sem trocar de aba.

Envio via Adobe Sign, com o segredo OAuth guardado num proxy n8n.

10–20 min → ~2 min por movimentação: de processo manual a revisão + geração, com a operadora já configurada.

Problema
Cada ticket pedia uma resposta padronizada, escolhida numa planilha de operadora × tipo de problema × resolução. A consulta era manual, com troca de aba em todo atendimento — e a linha errada virava o script errado enviado ao cliente.
Sistema
Extensão de navegador (Chrome/Edge) que lê o texto do ticket aberto, cruza com a planilha publicada em CSV por correspondência de prefixo e insere o script no campo de resposta quando o analista aciona. A planilha segue como fonte editável pelo time; nada roda em servidor.
Stack
JavaScript · MV3 · Google Sheets (CSV) · sem backend
4 passos → 1 cliquepor ticket — usado em produção até dar lugar ao FormPilot

05Em uso pelo time

FormPilot

Etapa 2
Problema
O esforço maior estava nas movimentações: cada inclusão, exclusão ou alteração exigia localizar o formulário da operadora, preencher campo a campo e enviar para assinatura num fluxo separado. E a extensão precisava ser instalada no navegador de cada analista.
Sistema
App nativo no Zendesk (ZAF), sem backend próprio. Lê os dados estruturados do ticket, usa a configuração da operadora (JSON) para estampar os campos no PDF via pdf-lib e envia para assinatura via Adobe Sign — com o segredo OAuth guardado num proxy n8n.
Papéis
Configuração uma vez por operadora, sem alterar código · Automação leitura do ticket, preenchimento e envio · Revisão humana antes de cada envio
Stack
ZAF · pdf-lib · Adobe Sign API · n8n
10–20 min → ~2 minpor movimentação: revisão + geração, já configurada
Abrir o case → ↳ FormPilot Studio: demonstração conceitual da etapa de configuração, dentro do case
Reaproveitado

A arquitetura sem backend, o matching por prefixo e as respostas rápidas configuráveis do TicketScript viraram a base técnica do FormPilot — não são dois projetos independentes, é um produto que passou por um segundo ciclo de aprendizado.

Documentos Verificáveis

Uma linha de planilha vira um documento que qualquer pessoa confere pelo QR code — sem ver dados pessoais.

Problema
Certificados e declarações de uma escola de cursos livres precisavam ser conferidos por terceiros, como as empresas clientes que acompanham os documentos dos funcionários, sem expor CPF, RG ou endereço dos alunos.
Sistema
Emissão dos PDFs a partir de uma planilha do Google, cada um com ID aleatório e QR code para uma página pública que mostra só os dados públicos e se o documento continua válido. Uma especificação, duas implementações: Python e n8n.
Stack
Python · Flask · ReportLab · n8n · Google Sheets
5 tipos de documentocom ID, QR code e validação pública · dados fictícios
