Por que não eliminar a planilha? Ela é o lugar certo para manter scripts — qualquer pessoa do time edita uma célula sem mexer no código. A extensão a torna invisível no fluxo diário, não obsoleta.
fluxo técnico

O que acontece entre o clique e a resposta.

01
Content script lê a página
Script injetado na plataforma de suporte captura texto via seletores DOM priorizados. Strings de domínio interno removidas antes da análise — um edge case encontrado em produção.
content.js · chrome.scripting
02
Texto normalizado
Acentos removidos via decomposição NFD. Convertido para minúsculas. Pontuação eliminada. "FleetEx" e "fleetex" viram o mesmo candidato — sem isso qualquer variação quebra o lookup.
normalizeText()
03
Valores cruzados com o CSV por prefixo
Matching via regex encontra valores mesmo quando o ticket usa variantes mais longas. Valores mais longos da planilha têm prioridade — regra necessária para evitar matches ambíguos com termos curtos.
detectValue() · regex prefixo
04
Injeção via setter nativo do React
Campo preenchido com o setter nativo compatível com React. Atribuição direta ao DOM deixa o campo visualmente preenchido mas funcionalmente vazio — o setter nativo dispara o evento corretamente.
executeScript · Object.getOwnPropertyDescriptor
arquitetura

Duas camadas. Nenhuma infraestrutura.

A camada de dados e a de execução são independentes. Qualquer uma pode mudar sem tocar na outra — nenhuma exige servidor.

📊

Camada de dados

Google Sheets · CSV público

🔗
Uma URL, sempre atualizada
Publicar na web → CSV. Qualquer pessoa do time atualiza scripts imediatamente sem tocar no código da extensão.
⚡
Cache diário
Dados baixados uma vez por dia e guardados no chrome.storage.local. Refresh manual disponível em Configurações.
🔓
Sem autenticação
CSV acessível publicamente. Nenhuma chave de API, nenhum OAuth, nenhuma credencial para gerenciar.
🔌

Camada de execução

Chrome / Edge · Manifest V3

🏠
Tudo local, no navegador
Nenhum servidor intermediário. A extensão lê a página, busca o CSV e preenche o campo — só isso.
📦
Zero dependências externas
Sem npm, sem bundler, sem build step. HTML + CSS + JS + APIs do Chrome. Parser CSV próprio — suporta campos com vírgulas entre aspas.
✏️
Respostas Rápidas configuráveis
Até 5 respostas configuradas pelo próprio usuário via editor contenteditable — negrito, itálico, listas, emojis. Copiadas como text/html via ClipboardItem, com fallback text/plain para ambientes sem suporte.
decisões de design

Trade-offs feitos de propósito.

Decisão
Justificativa
Trade-off aceito

CSV em vez de banco de dados

Scripts ficam numa planilha, não em banco ou endpoint de API.

✓ Zero infraestrutura. O time já usava planilhas. Novos scripts entram em produção em minutos, editados por qualquer um.

~ Sem sincronização em tempo real. Atualizações aparecem na próxima abertura do dia ou ao forçar atualização.

Sem backend

Tudo roda localmente. Zero componente server-side.

✓ Nada para hospedar, fazer deploy, monitorar ou pagar. Funciona offline após o primeiro fetch do dia.

~ Sem analytics centralizado nem logs. Diagnosticado via modo Debug embutido.

Matching por prefixo

Valor "envio" na planilha bate com "envios" no ticket.

✓ Valores na planilha ficam curtos e legíveis. Variações e plurais tratados automaticamente.

~ Valores mais longos têm prioridade para evitar matches ambíguos. Edge cases resolvidos via Debug.

evolução

O mesmo núcleo, um problema maior.

O TicketScript resolveu a resposta padronizada no ticket. O FormPilot levou a mesma base para o formulário de movimentação e a assinatura.

Etapa 1 · Fev–Mai 2025
⚡ TicketScript

Extensão de navegador que lê o ticket, cruza com a planilha publicada em CSV e insere o script no campo de resposta.

→
Etapa 2 · em uso pelo time
FormPilot

App nativo no Zendesk (ZAF): identifica operadora e movimentação, monta o formulário a partir da configuração da operadora e envia para assinatura via Adobe Sign.

10–20 min → ~2 min por movimentação
