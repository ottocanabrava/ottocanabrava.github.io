O problema

Uma planilha que precisava ficar aberta. Sempre.

Cada ticket exigia uma resposta padronizada em uma matriz de operadora × tipo de problema × resolução. A consulta era manual — e constante.

Antes — 4 passos em cada ticket

  1. Abrir o ticketIdentificar operadora, tipo de problema e resolução desejada.
  2. Trocar de aba para a planilhaPercorrer a matriz de combinações para encontrar a linha certa.
  3. Copiar o scriptA linha errada significa o script errado enviado ao cliente.
  4. Voltar e colarRepetir dezenas de vezes por dia.

Depois — mesmo ticket, um clique

1×Analisar → Inserir.

Script vai direto para o campo certo.

A planilha ainda existe. Só não precisa mais ficar aberta.

Por que não eliminar a planilha? Ela é o lugar certo para manter scripts — qualquer pessoa do time edita uma célula sem mexer no código. A extensão a torna invisível no fluxo diário, não obsoleta.

Fluxo técnico

O que acontece entre o clique e a resposta.

  1. 01Content script lê a páginaScript injetado na plataforma de suporte captura texto via seletores DOM priorizados. Strings de domínio interno removidas antes da análise — um edge case encontrado em produção.content.js · chrome.scripting
  2. 02Texto normalizadoAcentos removidos via decomposição NFD. Convertido para minúsculas. Pontuação eliminada. "FleetEx" e "fleetex" viram o mesmo candidato — sem isso qualquer variação quebra o lookup.normalizeText()
  3. 03Valores cruzados com o CSV por prefixoMatching via regex encontra valores mesmo quando o ticket usa variantes mais longas. Valores mais longos da planilha têm prioridade — regra necessária para evitar matches ambíguos com termos curtos.detectValue() · regex prefixo
  4. 04Injeção via setter nativo do ReactCampo preenchido com o setter nativo compatível com React. Atribuição direta ao DOM deixa o campo visualmente preenchido mas funcionalmente vazio — o setter nativo dispara o evento corretamente.executeScript · Object.getOwnPropertyDescriptor

Arquitetura

Duas camadas. Nenhuma infraestrutura.

A camada de dados e a de execução são independentes. Qualquer uma pode mudar sem tocar na outra — nenhuma exige servidor.

Camada de dados

Google Sheets · CSV público
  • Uma URL, sempre atualizadaPublicar na web → CSV. Qualquer pessoa do time atualiza scripts imediatamente sem tocar no código da extensão.
  • Cache diárioDados baixados uma vez por dia e guardados no chrome.storage.local. Refresh manual disponível em Configurações.
  • Sem autenticaçãoCSV acessível publicamente. Nenhuma chave de API, nenhum OAuth, nenhuma credencial para gerenciar.

Camada de execução

Chrome / Edge · Manifest V3
  • Tudo local, no navegadorNenhum servidor intermediário. A extensão lê a página, busca o CSV e preenche o campo — só isso.
  • Zero dependências externasSem npm, sem bundler, sem build step. HTML + CSS + JS + APIs do Chrome. Parser CSV próprio — suporta campos com vírgulas entre aspas.
  • Respostas Rápidas configuráveisAté 5 respostas configuradas pelo próprio usuário via editor contenteditable — negrito, itálico, listas, emojis. Copiadas como text/html via ClipboardItem, com fallback text/plain para ambientes sem suporte.

Decisões de design

Trade-offs feitos de propósito.

CSV em vez de banco de dadosScripts ficam numa planilha, não em banco ou endpoint de API.
Zero infraestrutura. O time já usava planilhas. Novos scripts entram em produção em minutos, editados por qualquer um.Trade-off aceito: sem sincronização em tempo real. Atualizações aparecem na próxima abertura do dia ou ao forçar atualização.
Sem backendTudo roda localmente. Zero componente server-side.
Nada para hospedar, fazer deploy, monitorar ou pagar. Funciona offline após o primeiro fetch do dia.Trade-off aceito: sem analytics centralizado nem logs. Diagnosticado via modo Debug embutido.
Matching por prefixoValor "envio" na planilha bate com "envios" no ticket.
Valores na planilha ficam curtos e legíveis. Variações e plurais tratados automaticamente.Trade-off aceito: valores mais longos têm prioridade para evitar matches ambíguos. Edge cases resolvidos via Debug.

Evolução

Este projeto evoluiu para o FormPilot.

O TicketScript foi a base conceitual e técnica do FormPilot — uma extensão que expandiu o mesmo núcleo (leitura de contexto no navegador + injeção de conteúdo + configuração via planilha) para automação de formulários de operadoras de saúde. A arquitetura sem backend, o matching por prefixo e as Respostas Rápidas configuráveis foram todos reaproveitados e evoluídos no projeto seguinte.
