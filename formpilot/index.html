o problema

Cada operadora, um formulário diferente. Nenhum atalho.

Toda solicitação de inclusão, exclusão ou alteração exigia localizar o modelo certo da operadora, preencher campo a campo e só então seguir para a assinatura.

antes — o mesmo esforço em todo chamado
Abrir o chamado
Ler o pedido do RH para identificar operadora, tipo de movimentação e dados do beneficiário.
Localizar o modelo certo
Encontrar, entre os modelos de cada operadora, aquele que corresponde ao tipo de movimentação pedido.
Preencher campo a campo
Digitar ou colar cada dado no lugar certo do formulário — um campo trocado significa retrabalho.
Enviar para assinatura
Anexar o documento pronto a um fluxo de assinatura separado e acompanhar manualmente o retorno.

Analisar → Gerar formulário → Enviar. O painel identifica a operadora e monta o restante.
Os modelos de cada operadora continuam existindo. Só deixam de exigir busca manual.
Por que manter um modelo por operadora? Cada operadora define seu próprio layout de formulário — isso não muda. A diferença é que o painel guarda essa regra como configuração, então adicionar uma operadora nova não exige reescrever nada, só descrever seus campos.
fluxo técnico

O que acontece entre o clique e a assinatura.

Quatro etapas independentes — cada uma pode mudar sem afetar as outras.

1
O painel lê o chamado
O texto do pedido é capturado e normalizado — variações de escrita e formatação não podem impedir a identificação do tipo de movimentação pedido.
leitura · normalização
2
Operadora e tipo de movimentação são identificados
O conteúdo é cruzado com uma lista de operadoras conhecidas para determinar qual modelo de formulário e quais campos usar.
detecção por configuração
3
O formulário é montado por coordenada
Cada campo tem uma posição definida no modelo daquela operadora; os dados do beneficiário são estampados diretamente no documento, sem servidor — tudo roda no navegador do analista.
geração client-side
4
Documento segue para assinatura via Adobe Sign
O documento pronto é enviado ao Adobe Sign para coleta de assinatura eletrônica. Como a autenticação OAuth exige um segredo que não pode ficar exposto no navegador, essa chamada passa por um pequeno fluxo de automação (n8n) que atua só como intermediário — o painel acompanha o retorno e atualiza o chamado automaticamente.
Adobe Sign · OAuth via n8n
arquitetura

Três camadas, cada uma trocável sozinha.

A ferramenta nasceu como extensão de navegador e hoje roda nativamente dentro da própria plataforma de atendimento, como um painel oficial via Zendesk App Framework (ZAF) — sem mais depender de nada instalado no navegador do analista. Configuração, painel e automação server-side seguem totalmente independentes entre si.

Configuração

Um arquivo por operadora

Operadora nova = arquivo novo
Adicionar uma operadora não altera nenhuma parte do painel — apenas descreve seus campos, posições e dependências entre eles.
Regras de dependência entre campos
Alguns campos só existem se outro campo tiver determinado valor — a configuração descreve isso explicitamente, para não haver campo preenchido "por engano" quando a condição não se aplica.

Painel nativo (ZAF)

Roda dentro da própria ferramenta de atendimento

Deixou de ser extensão de navegador
A versão anterior era uma extensão instalada no navegador de cada analista; hoje é um app oficial da plataforma, carregado automaticamente para todo o time, sem instalação individual.
Lê o chamado direto da plataforma
O painel usa o SDK oficial (ZAF) para ler os dados do chamado em que o analista está — sem depender de raspagem de tela.

Automação server-side

n8n como intermediário para Adobe Sign

Documento montado no navegador
A estampagem dos dados no PDF continua acontecendo no cliente; nenhum dado de beneficiário trafega por um servidor só para gerar o documento.
n8n cuida só do que exige segredo
Um fluxo de automação (n8n) guarda a credencial OAuth do Adobe Sign e faz a chamada em nome do painel — o segredo nunca chega ao navegador do analista.
decisões de projeto

Trade-offs que definiram a solução.

Escolhas concretas, com o que cada uma custou.

decisão
por quê
custo aceito

Configuração em vez de código por operadora

Operadora nova entra sem alterar o painel — só descrever seus campos.

Exige manter a configuração correta e testada a cada mudança de layout da operadora.

Montagem do documento no navegador

Nenhum dado de beneficiário passa por um servidor só para gerar o formulário.

Nenhum custo relevante — a operação é leve o suficiente para rodar no cliente.

Assinatura via Adobe Sign

Reaproveita uma infraestrutura de assinatura eletrônica já confiável e auditável, em vez de construir isso do zero.

Depende de disponibilidade e limites de uso de um serviço externo.

Migrar de extensão para app nativo (ZAF)

Elimina a instalação individual em cada navegador e centraliza atualizações para todo o time de uma vez.

Exigiu reescrever a camada de execução inteira para se adequar ao SDK oficial da plataforma.
