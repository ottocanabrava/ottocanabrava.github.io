Reprodução sem servidor. No FormPilot, o painel roda dentro da ferramenta de atendimento (Zendesk App Framework), monta o documento no navegador do analista e envia para o Adobe Sign por um fluxo n8n.

O problema

Cada operadora, um formulário diferente. Nenhum atalho.

Toda solicitação de inclusão, exclusão ou alteração exigia localizar o modelo certo da operadora, preencher campo a campo e só então seguir para a assinatura.

Antes — o mesmo esforço em todo chamado

  1. Abrir o chamadoLer o pedido do RH para identificar operadora, tipo de movimentação e dados do beneficiário.
  2. Localizar o modelo certoEncontrar, entre os modelos de cada operadora, aquele que corresponde ao tipo de movimentação pedido.
  3. Preencher campo a campoDigitar ou colar cada dado no lugar certo do formulário — um campo trocado significa retrabalho.
  4. Enviar para assinaturaAnexar o documento pronto a um fluxo de assinatura separado e acompanhar manualmente o retorno.

10–20 min por movimentação — processo manual, do início ao fim.

Depois — mesmo chamado, um painel

Identificar → Gerar → Revisar → Enviar

O painel identifica a operadora e monta o formulário; a revisão humana continua antes do envio.

Os modelos de cada operadora continuam existindo. Só deixam de exigir busca manual.

~2 min por movimentação — revisão + geração, com a operadora já configurada.

Por que manter um modelo por operadora? Cada operadora define seu próprio layout de formulário — isso não muda. A diferença é que o painel guarda essa regra como configuração, então adicionar uma operadora nova não exige reescrever nada, só descrever seus campos.

Fluxo técnico

O que acontece entre o clique e a assinatura.

Quatro etapas independentes — cada uma pode mudar sem afetar as outras.

  1. 01O painel lê o chamadoO texto do pedido é capturado e normalizado — variações de escrita e formatação não podem impedir a identificação do tipo de movimentação pedido.leitura · normalização
  2. 02Operadora e tipo de movimentação são identificadosO conteúdo é cruzado com uma lista de operadoras conhecidas para determinar qual modelo de formulário e quais campos usar.detecção por configuração
  3. 03O formulário é montado por coordenadaCada campo tem uma posição definida no modelo daquela operadora; os dados do beneficiário são estampados diretamente no documento, sem servidor — tudo roda no navegador do analista.geração client-side
  4. 04Documento segue para assinatura via Adobe SignO documento pronto é enviado ao Adobe Sign para coleta de assinatura eletrônica. Como a autenticação OAuth exige um segredo que não pode ficar exposto no navegador, essa chamada passa por um pequeno fluxo de automação (n8n) que atua só como intermediário — o painel acompanha o retorno e atualiza o chamado automaticamente.Adobe Sign · OAuth via n8n

Arquitetura

Três camadas, cada uma trocável sozinha.

A ferramenta nasceu como extensão de navegador e hoje roda nativamente dentro da própria plataforma de atendimento, como um painel oficial via Zendesk App Framework (ZAF) — sem mais depender de nada instalado no navegador do analista. Configuração, painel e automação server-side seguem totalmente independentes entre si.

Configuração

Um arquivo por operadora
  • Operadora nova = arquivo novoAdicionar uma operadora não altera nenhuma parte do painel — apenas descreve seus campos, posições e dependências entre eles.
  • Regras de dependência entre camposAlguns campos só existem se outro campo tiver determinado valor — a configuração descreve isso explicitamente, para não haver campo preenchido "por engano" quando a condição não se aplica.

Painel nativo (ZAF)

Roda dentro da própria ferramenta de atendimento
  • Deixou de ser extensão de navegadorA versão anterior era uma extensão instalada no navegador de cada analista; hoje é um app oficial da plataforma, carregado automaticamente para todo o time, sem instalação individual.
  • Lê o chamado direto da plataformaO painel usa o SDK oficial (ZAF) para ler os dados do chamado em que o analista está — sem depender de raspagem de tela.

Automação server-side

n8n como intermediário para Adobe Sign
  • Documento montado no navegadorA estampagem dos dados no PDF continua acontecendo no cliente; nenhum dado de beneficiário trafega por um servidor só para gerar o documento.
  • n8n cuida só do que exige segredoUm fluxo de automação (n8n) guarda a credencial OAuth do Adobe Sign e faz a chamada em nome do painel — o segredo nunca chega ao navegador do analista.

Arquitetura · demonstração

O formulário muda. O motor continua o mesmo.

No FormPilot, cada operadora define seu próprio layout de formulário — isso nunca muda. O que muda é que adicionar uma operadora deixou de significar escrever código: significa descrever, uma vez, onde cada campo fica e que regras ele segue. É essa configuração que um motor genérico interpreta para montar, preencher e validar o documento.

Formulários diferentes passaram a ser configurações de um mesmo motor, em vez de exigirem uma nova implementação a cada documento.

FormPilot é o projeto real. FormPilot Studio, logo abaixo, é a reconstrução conceitual e anonimizada dessa etapa de mapeamento — a mesma lógica de arquitetura usada no FormPilot, aplicada a um documento, operadora e dados fictícios, para mostrar como o motor funciona sem expor sistemas ou informações reais.

Configuração × operação
Mapear uma operadora nova é trabalho de configuração, feito uma vez — sem código novo. Depois de configurada, cada movimentação é uma operação: antes, 10 a 20 minutos de preenchimento manual; hoje, cerca de 2 minutos entre revisão e geração do documento. O ganho não é só velocidade — é menos exposição a erro de preenchimento e uma operação mais consistente entre analistas.

Decisões de projeto

Trade-offs que definiram a solução.

Escolhas concretas, com o que cada uma custou.

Configuração em vez de código por operadora
Operadora nova entra sem alterar o painel — só descrever seus campos.Custo aceito: exige manter a configuração correta e testada a cada mudança de layout da operadora.
Montagem do documento no navegador
Nenhum dado de beneficiário passa por um servidor só para gerar o formulário.Custo aceito: nenhum custo relevante — a operação é leve o suficiente para rodar no cliente.
Assinatura via Adobe Sign
Reaproveita uma infraestrutura de assinatura eletrônica já confiável e auditável, em vez de construir isso do zero.Custo aceito: depende de disponibilidade e limites de uso de um serviço externo.
Migrar de extensão para app nativo (ZAF)
Elimina a instalação individual em cada navegador e centraliza atualizações para todo o time de uma vez.Custo aceito: exigiu reescrever a camada de execução inteira para se adequar ao SDK oficial da plataforma.
